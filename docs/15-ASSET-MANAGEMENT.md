# 15 — Asset Management

**Project:** CampusOps / School Operations Management SaaS  
**Phase:** 9  
**Status:** Design locked for implementation

## 1. Purpose

Asset Management tracks school-owned operational assets from registration through assignment, transfer, maintenance, and retirement.

CampusOps complements the existing School ERP. This phase does not build a full procurement, warehouse, or accounting system.

# 6. Asset Status

Use:

```text
AVAILABLE
ASSIGNED
UNDER_MAINTENANCE
RETIRED
```

Lifecycle:

```text
CREATE → AVAILABLE
AVAILABLE → ASSIGNED
ASSIGNED → AVAILABLE
ASSIGNED → UNDER_MAINTENANCE
AVAILABLE → UNDER_MAINTENANCE
UNDER_MAINTENANCE → AVAILABLE
UNDER_MAINTENANCE → ASSIGNED
AVAILABLE → RETIRED
ASSIGNED → RETIRED
UNDER_MAINTENANCE → RETIRED
```

`RETIRED` is terminal.

No arbitrary status PATCH.

The status must be changed through business operations.

---

# 7. Assignment Model

An asset can optionally be assigned to one active Staff member.

Assignment and department/location must remain internally consistent.

MVP rule:

- An asset may have zero or one assigned staff member.
- Assigned staff must belong to the same organization.
- Assigned staff must be active.
- Retired assets cannot be assigned.
- An asset under maintenance may not receive a new assignment.
- When an assigned asset enters maintenance, its existing assignment should be cleared as part of the transition unless the implementation explicitly preserves it as historical information.

Use domain history to preserve previous assignment information.

Do not create a separate many-to-many assignment system.

---

# 8. Department / Location

An asset may have:

- a department
- a free-text physical location

Examples:

```text
Department: Information Technology
Location: Block A - Server Room
```

Department, if supplied, must belong to the same organization.

Location is intentionally free text for the MVP.

Do not create a building/floor/room hierarchy yet.

# 9. Asset Code

Generate tenant-local human-readable codes:

```text
AST-000001
AST-000002
AST-000003
```

Requirements:

- generated by backend
- unique within organization
- never supplied by client
- concurrency-safe

Follow the established complaint/visitor code-generation pattern:

```text
pg_advisory_xact_lock
+
tenant-local sequence calculation
+
unique constraint
```

Use a dedicated lock namespace for assets.

Do not reuse another module's exact lock key without a distinct namespace.

# 10. Serial Number / Barcode / QR

These fields are identifying metadata.

### Serial number

Optional.

If supplied, it should be unique within an organization.

Recommended:

```text
UNIQUE (organizationId, serialNumber)
```

Use nullable uniqueness semantics so multiple assets can have no serial number.

### Barcode

Optional.

Recommended:

```text
UNIQUE (organizationId, barcode)
```

### QR code

Optional metadata string.

Recommended:

```text
UNIQUE (organizationId, qrCode)
```

Do not generate QR images in this phase.

If the QR value is supplied by the system or client, it must still be tenant-scoped and unique.

# 13. Maintenance

Create an `AssetMaintenance` domain record.

Suggested fields:

- id
- organizationId
- assetId
- maintenanceType
- description
- startedAt
- completedAt nullable
- cost nullable
- vendorName nullable
- remarks nullable
- createdByUserId
- createdAt
- updatedAt

Maintenance type can initially be:

```text
REPAIR
SERVICE
INSPECTION
OTHER
```

Rules:

- Maintenance belongs to the same tenant as the asset.
- Asset must exist in the current tenant.
- Starting maintenance changes asset to `UNDER_MAINTENANCE`.
- Completing maintenance returns asset to `AVAILABLE` or `ASSIGNED` according to the locked business rule below.

For Phase 9, use this simpler rule:

> Completing maintenance returns the asset to `AVAILABLE`.

If it previously had an assignee, that assignment is not automatically restored. The user may explicitly assign it again.

This avoids hidden state restoration.

Maintenance records are retained.

No physical delete of maintenance records.

---

# 14. Asset Transfer

Transfer means changing the operational ownership/location context of an asset.

A transfer may change:

- department
- location
- assigned staff

It must remain within the same organization.

Create an `AssetTransfer` domain record.

Suggested fields:

- id
- organizationId
- assetId
- fromDepartmentId nullable
- toDepartmentId nullable
- fromLocation nullable
- toLocation nullable
- fromStaffId nullable
- toStaffId nullable
- reason nullable
- transferredByUserId
- transferredAt

Rules:

- asset must belong to authenticated tenant
- destination department must belong to tenant
- destination staff must belong to tenant and be active
- retired asset cannot be transferred
- asset under maintenance cannot be transferred
- transfer updates the Asset row and creates transfer history atomically

A transfer is not merely an arbitrary PATCH.

---

# 15. Retirement

Retirement is terminal.

Required:

- retirement reason
- server-generated `retiredAt`
- actor

Rules:

- retired asset cannot be assigned
- retired asset cannot be transferred
- retired asset cannot enter maintenance
- retired asset cannot return to AVAILABLE
- retired asset remains readable
- history remains readable

Retirement should be a dedicated business endpoint.

No physical deletion.

---

# 17. Database Design

Recommended models:

```text
AssetCategory
Asset
AssetMaintenance
AssetTransfer
AssetHistory
```

### Asset constraints

```text
UNIQUE (organizationId, assetCode)
UNIQUE (organizationId, serialNumber) where serialNumber is present
UNIQUE (organizationId, barcode) where barcode is present
UNIQUE (organizationId, qrCode) where qrCode is present
```

Use partial unique indexes where PostgreSQL semantics require nullable uniqueness to be explicit, following the existing project convention.

Indexes should support:

```text
organizationId + status
organizationId + categoryId
organizationId + departmentId
organizationId + assignedStaffId
organizationId + serialNumber
organizationId + barcode
organizationId + createdAt
```

History:

```text
organizationId + assetId + createdAt
```

Maintenance:

```text
organizationId + assetId + startedAt
```

Transfers:

```text
organizationId + assetId + transferredAt
```

Use restrictive business foreign keys.

# 20. Transaction / Concurrency Rules

High-risk mutations require transactions and row locking:

- assign
- unassign
- transfer
- maintenance start
- maintenance completion
- retirement

Pattern:

```text
BEGIN
→ tenant-scoped SELECT ... FOR UPDATE
→ validate current state
→ validate related records
→ mutate asset
→ write domain history
→ COMMIT
```

Concurrent conflicting operations must not bypass lifecycle rules.

Examples:

- concurrent retirement → exactly one succeeds
- retirement vs assignment → one operation serializes and the second sees RETIRED
- maintenance start vs retirement → operations serialize
- transfer vs retirement → operations serialize

Do not use Redis or distributed locking.

---

# 21. Tenant Isolation

Every query must derive organizationId from authenticated context.

Never trust client organizationId.

Validate all related IDs within the tenant:

- category
- department
- staff
- maintenance
- transfer
- history

Cross-tenant asset UUIDs must return 404.

Cross-tenant related IDs must fail validation without leaking existence.

# 26. Testing Strategy

## Backend unit/integration

### Creation
- asset created
- generated asset code
- AVAILABLE when no staff
- ASSIGNED when valid staff supplied
- correct initial history
- tenant isolation

### Category
- active same-tenant accepted
- inactive rejected
- cross-tenant rejected

### Staff
- active same-tenant accepted
- inactive/offboarded rejected
- cross-tenant rejected

### Metadata
- duplicate serial blocked within tenant
- duplicate barcode blocked within tenant
- duplicate QR blocked within tenant
- same identifiers allowed across tenants

### Assignment
- assign AVAILABLE asset
- reassign ASSIGNED asset if allowed by implementation
- unassign
- retired cannot assign
- maintenance asset cannot assign

### Transfer
- same-tenant destination accepted
- cross-tenant department/staff rejected
- retired cannot transfer
- maintenance cannot transfer
- transfer history created

### Maintenance
- start maintenance
- assignment cleared when maintenance starts
- complete maintenance
- double completion rejected
- retired cannot enter maintenance
- maintenance history created

### Retirement
- retirement succeeds
- assignment cleared
- server-generated retiredAt
- reason required
- repeat retirement rejected
- retired asset remains readable

### Concurrency
At minimum:

- concurrent retirement
- retirement vs assignment
- maintenance start vs retirement

Use real PostgreSQL concurrency tests where practical, not sequential simulations.

### Tenant isolation
Tenant B cannot:
- list Tenant A assets
- GET Tenant A asset
- assign/transfer/maintain/retire Tenant A asset
- access Tenant A history
- use Tenant A related IDs

### RBAC
Test missing permissions for each mutation class.
